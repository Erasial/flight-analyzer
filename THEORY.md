# Теоретичне обґрунтування математичних перетворень у проєкті

Цей документ пояснює математичні моделі, перетворення координат, інтегрування IMU, джерела похибок та обмеження, що використовуються в застосунку аналізу польотних логів.

## 1. Системи координат і позначення

У проєкті використовуються кілька систем координат:

- `WGS84` (геодезичні координати): широта `Lat`, довгота `Lng`, висота `Alt`.
- `ECEF` (Earth-Centered, Earth-Fixed): декартова система, пов'язана із Землею.
- `ENU` (East, North, Up): локальна декартова система відносно опорної точки.
- `Body frame` (корпус дрона): осі IMU, у яких вимірюються прискорення і кутові швидкості.
- `Earth frame` (умовно інерціальна локальна система): куди ми переносимо прискорення для інтегрування швидкості.

Ключова ідея: для адекватної інтерпретації руху потрібно узгодити всі виміри в одній системі координат.

## 2. Геодезичні обчислення

### 2.1. Дистанція між GPS-точками: формула гаверсинуса

Функція: `app/core/utils.py -> vectorized_haversine`.

Для сусідніх GPS-точок використовується:

- `a = sin^2(dlat/2) + cos(lat1) * cos(lat2) * sin^2(dlon/2)`
- `c = 2 * atan2(sqrt(a), sqrt(1-a))`
- `distance = R * c`, де `R = 6371 км`.

Чому це потрібно:

- Дає стабільну оцінку довжини траєкторії на сфері.
- Для малих відстаней похибка прийнятна для задач польотного аналізу.

Обмеження:

- Земля апроксимується сферою (не еліпсоїдом), тому є невелика систематична похибка.

### 2.2. Перетворення `WGS84 -> ENU`

Функція: `app/core/utils.py -> wgs84_to_enu`.

Кроки:

1. Береться опорна точка `(lat0, lon0, alt0)` як перший GPS-семпл.
2. Усі точки перетворюються в `ECEF` з параметрами еліпсоїда WGS84:
   - велика піввісь `a = 6378137.0`
   - ексцентриситет `e2 = 6.69437999014e-3`
3. Обчислюється різниця `d = [dx, dy, dz]` від опорної точки.
4. Застосовується матриця повороту `ECEF -> ENU`.

Чому це потрібно:

- `ENU` дає метри та інтуїтивні осі (`East/North/Up`) для 3D-графіків і локальної кінематики.
- Спрощує інтеграцію з IMU-оцінками швидкості.

Обмеження:

- Локальна система коректна в околі опорної точки; при дуже далеких польотах наближення гірше.

## 3. Орієнтація і перехід між `Body` та `Earth`

### 3.1. Матриця повороту за кутами Ейлера

Функція: `app/core/utils.py -> _rotation_body_to_earth`.

Застосовується послідовність `ZYX` (yaw, pitch, roll):

- `R = Rz(yaw) * Ry(pitch) * Rx(roll)`.

Це дає матрицю, яка переносить вектор з корпусної системи в земну.

Чому це потрібно:

- Прискорення IMU вимірюються в `Body frame`.
- Для фізично коректного інтегрування швидкості потрібні прискорення в `Earth frame`.

### 3.2. Чому не кватерніони (і коли краще перейти на них)

У реалізації зараз інтегруються кути Ейлера через гіроскоп. Це просто і прозоро, але:

- є ризик `gimbal lock` для кутів близьких до сингулярностей;
- чисельні похибки накопичуються швидше;
- компоновка поворотів залежить від порядку осей.

Кватерніони бажані, якщо:

- великі кути/агресивні маневри;
- довгі записи без зовнішньої корекції орієнтації;
- потрібна підвищена стійкість до сингулярностей.

## 4. Інтегрування IMU до швидкості

### 4.1. Трапецієподібна інтеграція

Функції:

- `app/core/utils.py -> cumulative_trapezoidal`
- `app/core/utils.py -> integrate_velocity_from_imu_trapezoidal`

Для кожної осі:

- `v(t_k) = v(t_{k-1}) + 0.5 * (a_k + a_{k-1}) * dt`.

Це точніше за прямокутну схему для шумних дискретних даних.

### 4.2. Компенсація гравітації

Після переведення прискорення в `Earth frame` віднімається константа:

- `g = 9.80665 м/с^2` по вертикальній осі.

Чому це потрібно:

- Акселерометр вимірює суму кінематичного прискорення і гравітації.
- Без віднімання `g` вертикальна швидкість буде фіктивно зростати.

### 4.3. Інтеграція орієнтації з гіроскопа

У поточній реалізації:

- `roll += gyro_x * dt`
- `pitch += gyro_y * dt`
- `yaw += gyro_z * dt`

Потім обчислюється матриця `Body -> Earth` і обертається вектор прискорення.

## 5. Походження дрейфу IMU (чому це нормально)

Важливий пункт для звіту і графіка порівняння швидкостей.

Причини дрейфу після інтегрування:

- біас акселерометра (`offset`) -> лінійно ростуча помилка швидкості;
- біас гіроскопа -> помилка орієнтації -> проекція `g` у горизонталь;
- шум і квантування -> випадковий дрейф;
- часові зсуви між GPS і IMU;
- неправильна одиниця гіроскопа (deg/s vs rad/s).

Тому крива `Accel-Derived Speed` очікувано розходиться з GPS з часом. Це не баг, а фізична властивість подвійної/послідовної інтеграції без зовнішньої корекції.

## 6. Практичні евристики в коді

### 6.1. Визначення одиниць гіроскопа

Функція: `app/services/pipeline.py -> _integrate_imu_velocity`.

Евристика:

- якщо `max(|gyro|) > 10`, вважаємо що це `deg/s` і переводимо в `rad/s`.

Ризик:

- у специфічних логах це може бути хибне спрацювання.

Покращення:

- читати одиниці з метаданих логера або `FMT`/конфігурації автопілота.

### 6.2. Фільтрація/згладжування IMU

Застосовується ковзне середнє (`window=5`) до `AccX/Y/Z` перед інтегруванням.

Плюси:

- знижує високочастотний шум.

Мінуси:

- фазовий зсув і втрата коротких динамічних піків;
- після `rolling(..., center=True)` крайні точки відкидаються (`dropna`).

### 6.3. Видалення outlier-ів через Z-score

Функція: `AnalysisService.filter_outliers`.

- Відсікаються значення з `|z| > threshold`.
- Це стабілізує метрики, але може прибрати реальні піки маневру.

## 7. Побудова земної поверхні (terrain)

Файл: `visualization/flight_plotter.py`.

### 7.1. ENU-квадрат для візуалізації

Будується квадратна XY-область:

- `span = max(span_x, span_y)`;
- додається запас `margin = 0.1 * span`;
- область центрується на траєкторії.

Це дає стабільний вигляд графіка і однаковий масштаб осей `X/Y`.

### 7.2. ENU -> Lat/Lng (локальна апроксимація)

Використовується наближення на малих відстанях:

- `lat = lat0 + north / R`
- `lng = lng0 + east / (R * cos(lat0))`

(з переведенням радіан/градусів).

Цього достатньо для локальних польотів; для великих дистанцій краще пряме геодезичне розв'язання на еліпсоїді.

### 7.3. Open-Elevation та кеш

- Висоти підтягуються батчами.
- Використовується кеш квантизованих координат (`1e-5` градуса).

Ефект:

- суттєве прискорення повторних побудов;
- менше мережевих запитів.

## 8. Метрики польоту: математичний зміст

Файл: `app/services/analyzer.py`.

- `Flight Duration`: `t_end - t_start`.
- `Distance Traveled`: сума сегментів гаверсинуса.
- `Max Horizontal Speed`: `max(|Spd|)`.
- `Max Vertical Speed`: `max(|VZ|)`.
- `Max Altitude`: `max(Alt)`.
- `Elevation Gain`: сума лише додатних приростів `Alt`.
- `Sample Rate`: `1 / mean(diff(TimeUS))`.

## 9. Синхронізація часових рядів і порівняння швидкостей

У графіку дрейфу GPS та IMU подаються у спільній часовій шкалі від спільного `t0`.

Наслідок:

- візуально видно розбіг, але це не строгий state-estimation ф'южн.
- для строгої оцінки похибки потрібні інтерполяція на спільну сітку та оцінка часового лагу.

## 10. Обмеження поточної моделі

1. Інтегрування орієнтації лише за гіроскопом без корекції магнітометром/GPS/фільтром.
2. Кути Ейлера замість кватерніонів.
3. Немає компенсації біасів IMU (алібрування перед інтегруванням).
4. Немає ZUPT/обнулення швидкості на стоянці.
5. Terrain-запити залежать від зовнішнього API.

## 11. Рекомендовані покращення

1. Перейти на кватерніони + комплементарний/Калман фільтр (`gyro + acc + mag + gps`).
2. Додати оцінку і віднімання біасів IMU на стаціонарних ділянках.
3. Додати ZUPT/детектор статичних фаз для обмеження дрейфу.
4. Використати інтерполяцію GPS/IMU на спільну часову сітку перед порівняннями.
5. Для далеких маршрутів застосувати точні геодезичні формули на еліпсоїді для `ENU <-> geodetic`.

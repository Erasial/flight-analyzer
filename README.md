## Аналізатор польотних даних

Веб-застосунок на Streamlit для розбору логів ArduPilot `.BIN`, обчислення метрик польоту, візуалізації 3D-траєкторії та формування звітів.

## Чому обрано саме цей стек

- `pymavlink`: найприродніший вибір для парсингу ArduPilot/MAVLink логів, бо напряму працює з форматом телеметрії.
- `pandas`: ефективні табличні перетворення, фільтрація, агрегації і підготовка даних для метрик/графіків.
- `numpy`: швидкі чисельні обчислення (тригонометрія, інтегрування, векторні формули, геометричні перетворення).
- `plotly`: інтерактивні 2D/3D-графіки (траєкторія, порівняння швидкостей, hover-дані, керування масштабом).
- `streamlit`: швидкий спосіб зібрати аналітичний UI без важкого фронтенду.
- `google-generativeai`: генерація текстового підсумку польоту на основі обчислених метрик.
- `reportlab` + `matplotlib`: стабільний експорт PDF зі структурованими таблицями та графічними сніпетами.

Цей стек добре закриває весь конвеєр задач: **парсинг -> обробка -> візуалізація -> аналітичний висновок -> експорт звіту**.

## Покроковий запуск

1. Перейдіть у корінь проєкту:

```bash
cd /path/to/test_task_challenge
```

2. Створіть та активуйте віртуальне середовище:

```bash
python -m venv .venv
source .venv/bin/activate
```

3. Встановіть залежності:

```bash
pip install -r requirements.txt
```

4. (Опційно) додайте Gemini API ключ для AI-аналізу:

```bash
export GEMINI_API_KEY="your_key_here"
```

5. Запустіть застосунок:

```bash
PYTHONPATH=. streamlit run web/streamlit_app.py
```

6. У UI:
- оберіть локальний `.BIN` або завантажте файл,
- натисніть `Завантажити дані`,
- перегляньте вкладки `Підсумок`, `3D-траєкторія`, `Дрейф швидкості`,
- за потреби сформуйте `AI-аналіз` і експортуйте `CSV/PDF`.

## 3D поверхня землі

- 3D-траєкторія може відображати рельєф через Open-Elevation API.
- За замовчуванням використовується Open-Elevation (потрібен інтернет).
- Відображення поверхні можна вимкнути у бічній панелі.

## Експорт

- У вкладці `Підсумок` доступно:
	- експорт метрик у `CSV`;
	- експорт повного звіту у `PDF`.
- PDF містить:
	- таблицю метрик;
	- зведення телеметрії;
	- AI-аналіз (якщо його було згенеровано в поточній сесії);
	- приклад графіка дрейфу швидкості;
	- приклад 3D-траєкторії з фіксованого ракурсу.

## Перевірка цілісності BIN

CLI повертає окремі коди для якості вхідного журналу:

- `0` — журнал декодовано без виявлених проблем;
- `2` — частковий результат (`PARTIAL`), метрики слід трактувати обережно;
- `3` — журнал відхилено (`REJECTED`), придатних даних недостатньо;
- `1` — інша помилка аналізу.

Якщо відомий еталонний розмір або SHA-256 оригіналу, передайте їх для виявлення
синтаксично коректного обрізання чи підміни файла:

```bash
python main.py flight.BIN \
  --no-plot \
  --expected-size 2932736 \
  --expected-sha256 33734e4050e95f6e95ec55bbcae4342d15cd60b03e5c1c88657f4500717886a4
```

Зовнішні regression-тести корпусу C01–C05 запускаються так:

```bash
UAV_LOG_CORPUS=/mnt/c/uav-log-corpus \
python -m unittest tests.test_corrupt_corpus -v
```

Без довіреного розміру або хешу неможливо гарантовано відрізнити файл, акуратно
обрізаний на межі повного DataFlash-запису після `DISARM`, від коректно завершеного
журналу. Статус `COMPLETE` означає відсутність виявлених проблем декодування, а не
криптографічне підтвердження повноти джерела.

За замовчуванням парсер зберігає лише типи повідомлень, потрібні поточному
аналізатору: `GPS`, `IMU`, `ATT`, `MSG`, `EV`, `MODE`, `ERR`. Це суттєво зменшує
використання пам'яті на великих логах. Для спеціалізованого повного розбору всіх
типів можна явно створити `BinaryDataParser(message_types=None)`.

## Якість телеметрії та довіра до метрик

Після декодування аналізатор окремо перевіряє потоки GPS та IMU. До розрахунків
не допускаються записи з нечисловим або від'ємним `TimeUS`, дубльованими чи
ізольовано пошкодженими часовими мітками, неправдоподібними координатами,
швидкістю, висотою, прискоренням або кутовою швидкістю. Розриви часової шкали та
IMU clipping реєструються як попередження.

Кожний потік отримує статус `GOOD`, `WARNING`, `POOR` або `UNUSABLE`. Метрики,
побудовані з цього потоку, отримують відповідний рівень довіри:

- `HIGH` — потік `GOOD`;
- `MEDIUM` — потік `WARNING`;
- `LOW` — потік `POOR`;
- `UNAVAILABLE` — потік відсутній, непридатний або джерело метрики невідоме.

CLI показує довіру поруч із кожною метрикою. API повертає повні об'єкти
`data_quality` та `metric_quality`, а Streamlit показує таблицю відхилених записів
і причини зниження довіри. Код завершення CLI `2` означає, що BIN частково
декодовано або якість хоча б одного потоку нижча за `GOOD`.

## Детектор польотних подій

Аналізатор формує хронологію з первинних потоків `MSG`, `EV`, `MODE`, `ERR` і
`GPS`. Підтримуються:

- ARM, DISARM, takeoff та завершені або незавершені ARM–DISARM сегменти;
- зміни режимів із числовим `ModeNum` та `Rsn`;
- RC, GCS, battery, EKF, terrain, vibration і dead-reckoning failsafe;
- втрата GPS fix після раніше здорового стану;
- battery low/critical та geofence breach;
- сирі помилки підсистем ArduPilot із `Subsys` та `ECode` як доказами.

Події з дубльованими доказами `MSG`, `EV` і `ERR` об'єднуються. AutoTest-службові
повідомлення на кшталт `GCS:AT-... Waiting for text` не трактуються як реальні
failsafe. API повертає звіт у полі `flight_events`, CLI друкує обмежену часову
шкалу (`--event-limit`), а Streamlit має окрему вкладку `Події`.

Поточні правила перевірені на ArduPilot `409226a6`: SITL S06, S07, S09 та
AutoTest AT06/AT10 збігаються з ground truth за типами, часом і кількістю подій.
Текстові правила залежать від формулювань ArduPilot і мають повторно
валідуватися для інших версій прошивки.

`SIM Hit ground` позначається лише як SITL ground contact. Це не є універсальним
детектором удару чи crash для реального польоту. Для реального борта такий висновок
має окремо підтверджуватися IMU, вертикальною швидкістю, станом двигунів і
послідовністю ARM/DISARM.
